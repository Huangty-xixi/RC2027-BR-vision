## 0. 结论：每台车 7 个节点

**决策只有一个节点（`mission_fsm`），其余 6 个要么只报事实、要么只执行、要么只提建议。**

| # | 节点 | 包 | 干什么 | 频率 | 为什么必须独立成进程 |
|---|---|---|---|---|---|
| 1 | `mcu_bridge` | rc2027_hw | 跟板子说话（下行命令、上行状态） | 收发 100 / 上报 200 Hz | 全车唯一持串口；仿真时要换成 `gazebo_bridge`（标准 3） |
| 2 | `odom_fusion` | rc2027_state | 算位姿 + 判断在哪一层（地面 / L1 / 传递区 / L2 / 重试区） | 50 Hz | 持续高频计算；真车与仿真要换数据源（标准 2、3） |
| 3 | `vision_detector` | rc2027_perception | 看方块（塔基/中段/塔顶/五色石）、看建塔处、看塔顶颜色 | 15–30 Hz | 要能录视频回放单独测；占 GPU（标准 1、2） |
| 4 | `mission_fsm` | rc2027_mission | **决策**：什么时候干什么。内含保护法则、携带上限、交接、重试四个模块 | 20 Hz | 唯一决策者 |
| 5 | `build_planner` | rc2027_mission | 选哪个建塔处（打分表：分值 + 公共格 + 距离 − 风险） | 1 Hz | 参数多，要能单独调参、离线测（标准 1） |
| 6 | `chassis_controller` | rc2027_control | 让车走：速度、定点（`goto_pose`）、航向保持 | 100 Hz | 闭环频率高（标准 2） |
| 7 | `mechanism_controller` | rc2027_control | 升降、夹爪、翻顶 | 50~100 Hz | 与底盘不同执行器、不同频率（标准 2） |

TR 同样 7 个（同一批包，配置不同）。

厂家驱动节点（相机、雷达、SLAM）是现成包，不在这 7 个里。

### 0.1 起进程的三条标准

满足一条才拆成独立节点；三条都不满足就合并：

1. **能单独喂数据测它吗** —— 把相机那段录下来回放，只测它一个。
2. **频率差一个数量级吗** —— 视觉 30 Hz / 串口 100 Hz / 电流环 1 kHz；差太多不塞进一个程序。
3. **要能单独换、单独关吗** —— 仿真时只换"看路的"和"传话的"。

### 0.2 从 18 个精简到 7 个：改了什么

之前那份清单按"**每条规则一个负责人**"拆，那是**代码里分模块**的标准；起进程要用上面三条。两件事混在一起，就把"两个 if"也拆成了节点。

| 原方案节点 | 现在 | 依据 |
|---|---|---|
| `carry_manager`（携带上限） | 并进 `mission_fsm` 的内部模块 | 就两个 if，三条都不满足 |
| `protection_guard`（保护法则） | 并进 `mission_fsm` 的内部模块 | 就一个 if |
| `retry_manager`（重试） | 并进 `mission_fsm` 的内部模块 | 本来就是流程里的一个阶段 |
| `handoff_coordinator`（交接） | 并进 `mission_fsm` 的内部模块 | 同上，是阶段 |
| `scoreboard`（自估分） | 删除 | 非必需 |
| `zone_monitor`（判区域） | 并进 `odom_fusion` | 纯几何计算，输入就是位姿 |
| `heading_hold`（航向保持） | 并进 `chassis_controller` | 同执行器、同频率 |
| `goto_controller`（定点导航） | 并进 `chassis_controller` | 只是底盘的一个模式，不是新进程 |
| `slot_detector`（看建塔处） | 并进 `vision_detector` | 同一张图、同一块 GPU |
| `joy_to_cmd`（手柄） | 手柄接收机在板子上，由 `mcu_bridge` 转发 | 不新增节点 |
| `pick_planner`（TR 拾取） | 并进 TR 自己的 `mission_fsm` | 同一套阶段机，配置不同 |

**18 − 11 = 7。功能一个没少，模块照旧分开写，只是不各起一个进程。**

### 0.3 五条设计要点

1. **两台车各一套独立栈**，互相不通信。规则 11.10 禁止 TR 与 BR 之间无线传输，交接只能靠视觉/机械对齐。
2. **BR 必须全自主**（规则 11.3），所有决策在 BR 自己的电脑上，不依赖人手或另一台车。
3. **算法在电脑、实时在板子**：电流环 1 kHz 留板子；流程/导航/视觉 10~100 Hz 在电脑。
4. **real / sim 两套数据源、算法节点只有一份**（照四足 `legged_ws` 的 real/ 与 sim/ 做法）。
5. **沿用 26 赛季的桥节点位置**：`serial_bridge` → `mcu_bridge`，帧格式 `0xA5 0x5A` 继续用，只扩命令字。

## 1. 规则给架构的硬约束

每条规则都必须有落点；落点可能是独立节点，也可能是 `mission_fsm` 里的一个模块。

| 规则条款 | 约束 | 落点 |
|---|---|---|
| 3.4.3 / 3.4.4 | TR 最多带 3 个、BR 最多 2 个；带五色石时不能带别的 | `mission_fsm`.carry_check（内部模块） |
| 3.5.2 / 8.1.6b | 必须严格 塔基 → 中段 → 塔顶 顺序 | `build_planner` + `mechanism_controller` |
| 3.5.6 / 8.1.4 | 塔顶按**顶面颜色**判归属，可翻转夺取 | `vision_detector`（报颜色）+ `build_planner`（决定翻不翻） |
| 3.6.1 / 4.5.1 | 保护法则：≥2 座全塔且 ≥1 在 L1 公共区或 L2，才有资格取五色石 | `mission_fsm`.protection_check（内部模块） |
| 3.2 / 4.3 | TR 只能在地面；BR 不得下地面（起步/重试除外） | `odom_fusion`（报区域）+ `mission_fsm`（用） |
| 3.4.5 / 6.3 | 交接只能发生在传递区，且用品必须完全进入传递区 | `mission_fsm`.handoff（内部模块） |
| 5.1 / 5.3 | 重试流程；BR 用 L1 重试区的前提是比赛中进过 L1；强制重试等 15s | `mission_fsm`.retry（内部模块） |
| 8.1.5 | 五色石放上中央基座 = 250 分，终极目标 | `mission_fsm` |
| 8.1.1 | TR 每送 1 个用品进传递区 = 5 分（裁判记录） | `mission_fsm`（自估，仅调试与策略参考） |
| 11.10 | TR 与 BR 禁止无线通信 | 两套独立栈 + 视觉/机械交接 |

## 3. 节点 / 话题 / 频率

命名空间：TR 用 `/tr`，BR 用 `/br`，下表 `{ns}` 代表其中一个。

| 节点 | 订阅 | 发布 | 频率 |
|---|---|---|---|
| `mcu_bridge` | `{ns}/motor_target`、`{ns}/mech_target`、`{ns}/mode_set`、`{ns}/heartbeat` | `{ns}/motor_state`、`{ns}/imu`、`{ns}/joint_states`、`{ns}/mcu_fault`、（TR）`{ns}/joy` | 收发 100 Hz、IMU 上报 200 Hz |
| `odom_fusion` | `{ns}/motor_state`、`{ns}/imu`、`/lidar/odom`（外部 SLAM） | `{ns}/odom`、`{ns}/zone_state` | 50 Hz |
| `vision_detector` | `/camera/color/image_raw`、`/camera/aligned_depth_to_color/*`、`/camera/camera_info` | `{ns}/blocks`、`{ns}/slots`；服务 `{ns}/set_detection` | 15–30 Hz |
| `mission_fsm` | `{ns}/zone_state`、`{ns}/odom`、`{ns}/blocks`、`{ns}/slots`、`{ns}/mcu_fault`、`{ns}/build_plan`、`/referee/events` | `{ns}/cmd_vel`、`{ns}/mech_command`、`{ns}/mission_state` | 20 Hz |
| `build_planner` | `{ns}/slots`、`{ns}/mission_state` | `{ns}/build_plan` | 1 Hz |
| `chassis_controller` | `{ns}/cmd_vel`、action `{ns}/goto_pose` | `{ns}/motor_target`（4 轮转速） | 100 Hz |
| `mechanism_controller` | `{ns}/mech_command` | `{ns}/mech_target` | 50 Hz |

### 3.1 `mission_fsm` 内部的四个模块（不单独起进程）

| 模块 | 管什么 | 规则 |
|---|---|---|
| `protection_check` | 保护法则够不够，够不够资格去取五色石 | 3.6.1 / 4.5.1 |
| `carry_check` | 手上几个、有没有超上限、携石时不带别的 | 3.4.3 / 3.4.4 |
| `handoff` | 传递区交接的阶段与判据 | 3.4.5 / 6.3 |
| `retry` | 卡住/故障/被判犯规后的重试流程 | 5.1 ~ 5.3 |

> 模块放在同一个进程里，照样"一条规则改一处"；好处是不用多起 4 个进程、不用多维护 4 份启动配置。

## 5. PC ↔ 板子 接口

沿用 26 赛季帧：`0xA5 0x5A` + **新增 2 字节序号**（判新旧，防乱序）。

```
帧 = 头(2) | 命令字(1) | 长度(1) | 序号(2) | 载荷(n) | 校验(1)
```

| 方向 | 命令字 | 名称 | 频率 |
|---|---|---|---|
| 下行 | `0x30` | `MOTOR_TARGET`（4 轮目标转速） | 100 Hz |
| 下行 | `0x31` | `MECH_TARGET`（升降 / 夹爪 / 翻转） | 50 Hz |
| 下行 | `0x32` | `MODE_SET`（使能 / 阻尼 / 关闭、控制模式） | 事件 |
| 下行 | `0x33` | `HEARTBEAT` | 10 Hz |
| 上行 | `0x40` | `MOTOR_STATE`（转速 / 电流 / 温度） | 100 Hz |
| 上行 | `0x41` | `IMU_RAW`（含时间戳） | 200 Hz |
| 上行 | `0x42` | `JOINT_STATE`（升降 / 夹爪关节角） | 100 Hz |
| 上行 | `0x43` | `FAULT_ESTOP`（故障码 / 急停 / 夹紧告警） | 事件 |
| 上行 | `0x44` | `ACK` | 事件 |

**带宽**：上行约 10~13 KB/s，已顶到串口 115200 天花板 —— 走 USB CDC 或波特率 ≥ 460800。

板子侧的夹紧、缓停、急停硬线、板子代码结构，见 `RC2027_下位机职责与接口.md`。

## 6. real / sim 怎么切

```
ros2 launch rc2027_bringup br.launch.py sim:=false   # 真车
ros2 launch rc2027_bringup br.launch.py sim:=true    # 仿真
```

| 层 | real | sim |
|---|---|---|
| 数据源 | `mcu_bridge`（USB CDC / 串口） | `gazebo_bridge`（Gazebo 关节状态 ↔ 同一组话题） |
| 物理 | 真车 | `rc2027_sim`：场地 + 机器人 + `ros2_control` |
| 裁判 | 真人裁判 | `referee_sim`（记分、保护法则、犯规、重试、出界） |
| 手柄 | 板子转发 | 键盘替身 |

`rc2027_sim` 的三个组件：

| 组件 | 内容 |
|---|---|
| 场地 | 地面区 / L1（+600）/ L2（+900）/ 坡道 3500×600 / 三级阶梯 / 建塔处 500² / 中央基座 800 高 / 五色石基座 500 高 / 储存区 1000×2000 / 两个公共区 |
| 机器人 | TR、BR 的 URDF + 底盘控制器 + 升降/夹爪位置控制器 |
| 裁判替身 | 按 8.1 记分、3.6.1 判保护法则、6.x 判犯规、5.x 处理重试、6.4 判出界 |

## 7. 落地顺序

1. **`rc2027_msgs` + `rc2027_description`**：先把接口和两台车的 URDF 定死（URDF 是后面所有仿真的前置）。
2. **`rc2027_hw` + `rc2027_state`**：让位姿、IMU、板子状态能在电脑上稳定拿到；同时写 `gazebo_bridge`，做到 `sim:=true` 能出数据。
3. **`rc2027_sim` 的场地与裁判替身**：按 2027 规则建场地（26 的场地不能直接用），裁判替身让流程能自动跑。
4. **`rc2027_control` + `rc2027_mission`**：把 26 赛季板子上的 `Process_Flow` / `app_zone*` / `retry` / 底盘控制搬上来，在仿真里跑通「取料 → 上坡 → 传递区交接 → 建塔 → 取五色石 → 上中央基座」整条链路。

## 8. 待定与风险

1. **一台电脑同时控两台车是否触碰 11.10**（TR 与 BR 禁止无线通信）。建议：两车各自一台电脑、各自一套栈，交接靠视觉/机械，不做任何链路对接；如需统一，必须先向组委会确认。
2. **Nav2 的适用范围**：L1、L2 是平整平台，2D 导航够用；坡道与阶梯（600mm 高差）要单独做爬坡/上台阶控制，不能用 2D 代价地图解决。
3. **五色石是 ⌀200 的球**（可用 4 号足球），夹持机构与塔基/中段完全不同，`mechanism_controller` 要区分两套动作。
4. **塔顶翻面策略**（3.5.8）能抢对方 40/80 分，规则允许且划算，`build_planner` 要显式支持。
5. **手柄路径**：默认走板子（由 `mcu_bridge` 转发），省一个节点；若改为插电脑，需要补第 8 个节点。
6. 26 赛季遗留：两套导航并存、大量 `xxx copy.py`、0 字节占位文件，27 赛季开局就要定目录与命名规范。
